# Обробка збоїв

Принцип один: **`classify()` ніколи не кидає виняток.** Вона завжди повертає
`Classification` — успішний або із заповненим `error`. Помилка тут це значення,
а не аварія.

Причина конкретна. Тікети обробляються паралельно через
`ThreadPoolExecutor.map()`, який обриває весь батч, якщо хоч один виклик кине
виняток. Один тікет, якому не пощастило з 429, убив би обробку всіх інших.

## Матриця збоїв

| Збій | Де ловиться | Поведінка | Fallback |
|---|---|---|---|
| **Rate limit (429)** | SDK, потім `RateLimitError` | SDK сам робить до 3 ретраїв з експоненційним бекофом; якщо всі вичерпані — помилка як значення | тікет → tier-1 підтримка, P2, review |
| **Серверна помилка (5xx)** | SDK, потім `APIStatusError` | те саме: ретраї в SDK, далі значення з кодом і типом помилки | те саме |
| **Timeout** | `APIConnectionError` | ліміт 60 с на запит; `APITimeoutError` є підкласом `APIConnectionError`, тож ловиться тим самим блоком | те саме |
| **Мережа недоступна** | `APIConnectionError` | ретраї SDK, далі значення | те саме |
| **Невірна модель (404)** | `NotFoundError` | ретраїв немає — це помилка конфігурації, не тимчасова | те саме, але помітно в логах як `model not found` |
| **Invalid JSON (тільки V1)** | `_parse_freeform()` | три окремі випадки: JSON не знайдено, не парситься, не об'єкт | те саме |
| **Значення поза словником** | `_validate_against_taxonomy()` | пишеться в `schema_violations`; для V2/V3 неможливе — схема не дозволяє | правило `invalid_model_output` → review |
| **Будь-що непередбачене** | catch-all `except Exception` | напр. помилка валідації Pydantic або несподівана форма відповіді | те саме |

## Fallback: тікет не зникає і не вгадується

Коли класифікація не вдалася, `policy.fallback_decision()` повертає:

```python
Decision(
    category="unclear_other",
    priority="P2",
    action="route_to_general_support",
    requires_review=True,
    review_reasons=["automatic classification failed: <причина>"],
    applied_rules=["classification_failed"],
)
```

Три рішення закладені сюди свідомо:

**P2, а не P0 і не P3.** Ми не знаємо, що в тікеті. P0 забив би чергу термінових
при масовому збої API; P3 сховав би справжню аварію на два дні. P2 — це рівень,
який не припускає ні того, ні іншого.

**Черга людей, а не повторна спроба.** Ретраї вже вичерпані всередині SDK. Далі
має працювати людина, а не ще один цикл.

**Причина видима.** Агент бачить, що класифікація не спрацювала і чому, а не
порожню картку без пояснення.

Це не теорія: під час розробки виявилось, що `messages.parse()` не приймає
top-level `cache_control`, і всі 15 тікетів впали з `TypeError`. Батч не
обірвався — прогін завершився повним звітом із `api_errors: 15`, і всі 15 тікетів
були коректно змаршрутизовані на людей. Catch-all перетворив би падіння на
інцидент; він перетворив його на рядок у звіті.

## Ретраї: свого циклу немає навмисно

Клієнт створюється з `max_retries=3` і `timeout=60.0`. SDK сам повторює 429, 5xx
і мережеві помилки з експоненційним бекофом.

Власний retry-цикл поверх цього був би другим і гіршим: подвоєна кількість спроб,
подвоєний час очікування, і при цьому без урахування заголовка `retry-after`,
який SDK читає.

Обмеження, яке варто знати: таймаути теж ретраяться, тож у найгіршому випадку
один виклик може зайняти `timeout × (max_retries + 1)` = до 4 хвилин. Для
класифікатора в фоновому режимі це прийнятно; для синхронного шляху в UI
`timeout` треба знижувати.

## Ланцюг except, а не один загальний

```python
except anthropic.NotFoundError      # 404 — конфігурація, ретраїти марно
except anthropic.RateLimitError     # 429 — ретраї вже були, тепер це сигнал про ліміти
except anthropic.APIStatusError     # будь-який інший не-2xx
except anthropic.APIConnectionError # мережа і таймаути
except Exception                    # усе решта — щоб батч не впав
```

Порядок від конкретного до загального. Один `except APIStatusError` на все
втратив би різницю між тимчасовим і фатальним: 404 через одруковану назву моделі
й 429 через сплеск трафіку виглядали б однаково, хоча перше треба чинити в
конфізі, а друге — чекати.

## Чого тут немає

- **Circuit breaker.** При тривалій недоступності API система продовжує
  надсилати запити й отримувати помилки. На продакшн-обсягах потрібен розмикач,
  який після N підряд збоїв перестає пробувати й відправляє потік одразу на
  людей.
- **Черга з повторною обробкою.** Тікет, який не вдалося класифікувати, іде до
  людини назавжди. Правильніше — спробувати ще раз через кілька хвилин і лише
  потім віддавати людині.
- **Алертів.** `api_errors` рахується у звіті, але нікуди не сигналить.
- **Ідемпотентності.** Повторний запуск на тому самому наборі створить нові
  записи. Для прототипу байдуже, для інтеграції з хелпдеском — ні.
